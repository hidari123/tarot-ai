# Mystic Tarot · 产品扩展：双模式 / 运势矩阵 / 问神谕（2026-11-04）

> **这一轮的定位**：第二轮优化（[optimization-analysis-2026-11.md](optimization-analysis-2026-11.md)）
> 把「怎么跑得更快更省」解决完了。瓶颈随之转移到一个更根本的问题：
> **产品本身够不够完整？**
>
> 竞品对标的结论（详见 §一）：
> 我们的占卜**质量不输**，但**入口太窄** —— 用户必须先想清楚问题、
> 才有资格用。竞品（Tarot Run 的 Oracle、Tarotap 的 5 种运势）都提供了
> 「更轻的入口」。
>
> 所以这一轮做的是**扩展产品面**，三个方向：
> **B 双模式**（同一件事的两种节奏）、**C 运势矩阵**（免提问的内容线）、
> **D 问神谕**（免抽牌的对话线）。

### 竞品原话（作为设计依据）

**Tarotap 的快速模式**：
> 「午休只有幾分鐘？快速解讀直接給你重點。如果是比較重要的事，
> 切換到深度模式，AI 會花更多時間比對牌跟牌之間的關係」

→ 这就是 B 的产品定义：**快速模式不是"少讲几句"，是"换一套仪式路径"**。

**Tarot Run 的 Oracle**：
> 「無論是剛抽到的牌、看不懂的牌陣，還是想理清的處境，都可以直接提問」
> 「可以追問 —— 一次解讀往往不夠。神諭會記住上下文」

→ 这就是 D 的产品定义：**最低门槛的入口**（不需要想清楚问题）。

**Tarotap 的第一差异化**：
> 「你不用自己选牌阵」

→ 我们**本来就没有牌阵货架**（用户只需描述问题）—— 这一点不用改。

## 二、B 方向：双模式（快速一问 / 深度解读）

**提交**：`b94765a`

### 实测效果

| | 快速一问 | 深度解读 |
|---|---|---|
| HITL 交互次数 | **3 次** | 12 次 |
| LLM 轮次 | **8 轮** | 17 轮 |
| 工具调用 | **8 次** | 15 次 |
| 耗时 | **61s** | 83s |
| 单场成本 | ≈ ¥0.29 | ≈ ¥0.58 |

快速模式工具序列（干净、无重复）：
```
承约 → 选牌 → 抽牌 → 检索 → 揭示 → 一次讲完 → 综合 → 收束
```

### 设计要点

**模式 = 仪式路径的子集**（不只是"文案短一点"）：
- 快速：跳过呼召三问 / 不逐张翻牌提问 / 一次讲完 3 张
- 深度：保持现有全部仪式节奏

**承约在两种模式下都保留** —— 它是仪式核心：
把「我的运势怎么样」收敛成一个**牌能回答的具体问题**。

### 实现中踩过的三个坑

**坑 1：守卫死锁（最容易踩）**
快速模式跳过呼召 → 若守卫仍检查全部前置，「选牌」会被**永久拦截**。
→ `canEnter` 增加 `mode` 参数，按 `requiredPhases(mode)` 过滤前置集合。

**坑 2：模型不按批量参数调用**
给 `interpret_card` 加 `card_indexes`/`readings` 数组参数后，模型**依然逐张调用**
（3 张牌 = 3 轮）→ 快速模式撞 `max_rounds`。
根因：schema 里 `required: ["card_index", "reading"]` 强烈暗示"单张用法"，
模型对可选参数天然保守。
→ 解法：**快速模式换一组工具**（`interpret_all_cards`，required 只有数组），
模型没有"单张"选项。

**坑 3：临期催促来得太晚**
`LATE_ROUND = Math.max(10, MAX_ROUNDS - 6)` 的下限 10 对快速模式太晚
（流程需 11 轮，上限 14）→ 撞墙时 `perCardPending` 为 true → 催促根本没注入。
→ 下限按模式走；且催促文案按状态区分
（牌没讲完时催"立即 write_reading"会被守卫拦住 → 死循环）。

## 三、C 方向：运势矩阵

**提交**：`dc70daa`

### 内容矩阵

| 层级 | 牌数 | 更新 | LLM 成本 |
|---|---|---|---|
| 每日之牌 | 1 | 每天 | **0**（拼装） |
| 本周七牌 | 7 | 每周 | 0 |
| 月运（上/中/下旬） | 3 | 每月 | 0 |
| 四季牌阵（起点/展开/阻碍/转机/落点） | 5 | 每季 | 一次性 + 按季缓存 |
| 年运主题 + 12 个月流年 | 1 + 12 | 每年 | 一次性 + 全年缓存 |

**成本算术**：年运 17 次 LLM 调用/年 ≈ **¥0.2/年**
（对比「每天生成一次」= 365 次/年 ≈ ¥4.4/年，且质量没提升）

### 核心设计

**① 确定性选取（同一天永远同一张牌）**
随机会导致刷新就变 → 预生成失效 → SEO 归零 → URL 不可分享。
用日期字符串的 FNV-1a 哈希散列到 78 张牌上。
> 实测踩坑：周牌阵原来用「当前日期」做种子 → 周一与周日看到的不一样。
> 已改为用「周一日期」做种子。

**② 零成本文案拼装**
素材：78 张牌 × 1.8 万字（牌面故事 + 正逆位牌意 + 关键词）。
诚实说明：拼装文案不如 LLM 流畅，带点"典籍摘抄"的生硬感 ——
这是零成本方案的必然代价，对应补偿是高价值内容走 LLM 一次性生成。

**③ 分层：纯函数层（`build.ts`）与 server 层（`server.ts`）严格分开**
> 实测踩坑：客户端组件经 `build.ts` 间接引入 `db.ts`（better-sqlite3 原生模块）
> → 构建直接失败。

### PPR（Next 16）的四道坎

我们开了 `cacheComponents: true`（= PPR），实测踩到的**全部**规则：

| # | 现象 | 解法 |
|---|---|---|
| ① | `unstable value \`new Date()\` while prerendering` | 先 `await connection()` |
| ② | `uncached or runtime data during prerendering` | 动态部分放进 `<Suspense>` |
| ③ | Suspense 的 `fallback` 里也不能有 `new Date()` | fallback 只写静态文案 |
| ④ | **client 组件**里也不能有 `new Date()` | 首页改用 `/daily` 中转页（server 端算日期） |

> 补充：`redirect()` 也属于 runtime data → 必须放在 Suspense 边界内。

### 路由结构（SEO）

```
◐ /daily                    → 重定向到今天（server 端 308）
◐ /daily/[date]             → Partial Prerender
  ├ ○ /daily/2026-10-28     → 38 个完全静态（过去 7 天 + 未来 30 天）
  └ ◐ [+36 more paths]      → 其余走 ISR
◐ /fortune                  → 运势专区（入口页）
◐ /fortune/monthly          → 月运（零成本拼装）
◐ /fortune/seasonal         → 四季（LLM 一次性生成 + 缓存）
◐ /fortune/yearly           → 年运与流年（LLM 一次性生成 + 缓存）
```

实测缓存生效：`year:2026`（2133 B）与 `season:2026:秋`（824 B）均已落库。

## 四、D 方向：问神谕（免抽牌的对话式塔罗向导）

**提交**：`84a0327`

### 设计：不写第二个 Agent

神谕与占卜**共用同一个 `runAgent`**，只换三样东西：

1. **system prompt**（占卜向导 vs 对话式塔罗向导）
2. **可用工具集**（神谕没有抽牌类工具）
3. **阶段推进**（神谕不走仪式状态机）

其余（RAG / 人格 / 记忆 / 追问 / 情绪档案 / 审校）**完全复用**。

> 理由：写第二个 Agent 会导致两套 prompt、两套质量标准、两套 bug，
> 而且两套会慢慢漂移（改了占卜忘了神谕）。

### 核心：免抽牌是「能力层」禁用，不是 prompt 建议

prompt 说"别抽牌"只是**建议**；只要 `draw_cards` / `offer_card_selection` /
`reveal_card` 还在工具列表里，模型就**可能**去调用。
→ `ORACLE_TOOLS` 从**工具集**里剔除抽牌类 + 岔路类工具。

> **为什么连 `fate_crossroads` 也去掉**（实测踩坑）：
> 它是"占卜岔路"工具 —— 语义是"在牌阵岔路口让用户选一条路"，配套三张候选牌。
> 神谕里用它 → 模型会"替用户把三个方向都点一遍"再给一整套 2448 字长文 ——
> 违背"对话"本质，也**替用户做了选择**。

### 实测效果

| | 修复前 | 修复后 |
|---|---|---|
| 耗时 | 646.7s | **22.1s** |
| 回答长度 | 2448 字 | **938 字** |
| 工具序列 | rag×2 + ask_user + fate_crossroads | **rag×2** |
| 追问 | ✓ 上下文保留 | ✓ 上下文保留 |

### 神谕的三种场景

① **牌义问答** —— 「宝剑三和星星放一起是什么意思」→ 结合两张牌讲
② **处境倾诉** —— 先接住情绪，再给一个有落点的观察
③ **牌阵推荐** —— 说清各方式适合什么问题，给具体建议

### 实现中踩过的坑

**坑 1：纯文本回答被"首答纠偏"拦下**
占卜的"首答纠偏"逻辑是"模型没抽牌就回答 = 无效占卜"——
那**只对占卜成立**。神谕本来就不抽牌，走纠偏路径会被反复要求"去抽牌"
（而神谕没有抽牌工具）→ 死循环 → 用户看到"占卜师陷入沉思"。
→ 神谕的纯文本回答**直接结束**。

**坑 2：仪式阶段被反推成 contract**
恢复神谕会话时若按 `derivePhase` 反推 → 得到 `contract` → 触发承约守卫 → 卡死。
→ 神谕的仪式阶段恒为 `"done"`（新建与恢复都是）。

**坑 3：追问发错端点**
前端若重新发 `/api/interpret` → **新建一个会话** → 上下文丢失、
原会话永远卡在 busy → 追问全部 409。
→ 追问必须走 `/api/answer`（回填答案 → 后端继续推进 → 同一个 SSE 流继续输出）。

**坑 4：注释里写 `**/api/answer` 会让块注释提前闭合**（`*/`）→ 构建失败。
