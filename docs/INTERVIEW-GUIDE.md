## 0. 一分钟速览（电梯讲稿）

> 面试官：讲讲你做了什么？
>
> **我做了一个 AI 塔罗占卜应用，但它真正的技术点是把"不可控的 LLM 对话"包装成一个"可控的仪式流程"。**
>
> 架构上是 **Next.js 16 + 多 Agent 编排 + 混合 RAG + SSE 流式 + HITL**：
> - **多 Agent**：一个 Supervisor 主循环协调 5 个专职 Agent（契约/呼召/抽牌/解读/收束），每个 Agent 有自己的工具白名单
> - **RAG**：**BM25 + 向量检索 + RRF 融合**的混合检索，79 张牌的原文真实入库，命中片段带 `[n]` 编号注入 system prompt，答案里能追溯引用
> - **HITL**：所有阻塞点由前端渲染表单，后端把状态存快照，前端提交后从快照恢复 —— 而不是让 LLM "自己等着"
> - **SSE**：20+ 种事件类型，把"思考 / 检索 / 翻牌 / 提问 / 解读"全链路可视化
>
> **最能体现工程能力的两点**：
> 1. **状态机 + 快照恢复**：任何时刻断网/刷新，session 能从 SQLite 快照精确恢复到当前步骤，不丢状态、不重复扣费
> 2. **671 条自动化断言**：37 个 verify 脚本覆盖 Agent 协议、RAG、限流、音频、图标 —— 因为这类系统里"看起来能跑"和"真的能跑"差距巨大
>
> **最踩坑的一段**是环境音：用户说"很难听"，我用**离线渲染 + FFT 频谱分析**把主观感受变成客观指标（频谱重心从 2400Hz 降到 431Hz），由此定位到一个隐蔽的八度计算 bug —— 持续低音被算成了 220Hz（人耳最敏感区），这正是三个月前用户投诉过的"刺耳空鸣"的**根因**。

## 1. 项目背景与需求建模

### 1.1 产品是什么

一个**对话式塔罗占卜** Web 应用。用户提出困惑，AI 通过多轮对话完成一次"占卜仪式"，过程中会抽牌、让用户翻牌、解读牌意，最后给出综合结论。

### 1.2 关键的产品洞察：塔罗不是"查答案"，是"一场仪式"

这是整个项目所有技术决策的源头。传统塔罗 App 的模型是"选牌 → 出结果"，但真实塔罗体验是：

```
提问 → （占卜师复述/确认你的问题）→ 呼召 → 选牌 → 逐张翻牌 → 逐张解读 → 综合收束
```

这个顺序里有**多个必须等待用户输入的阻塞点**。这直接决定了技术架构：

| 产品需求 | 技术含义 |
|---|---|
| 占卜师先复述问题、用户确认 | 需要**阻塞式交互**（LLM 停下等用户） |
| 用户亲手翻牌 | 需要**前端交互 + 后端状态同步** |
| 逐张解读（不是一次性全出） | 需要**流式增量输出**，不是一个大 JSON |
| 中途关掉页面再回来 | 需要**服务端状态持久化 + 快照恢复** |
| 过程要有"仪式感" | 需要**视觉/音频/动效随阶段变化** |

> ⚠️ **如果我只是做一个"输入问题 → 返回解读"的页面，上述全部技术都不需要。**
> 正是因为要做"仪式"，才有了多 Agent、状态机、SSE、HITL、快照恢复。

### 1.3 需求分层

| 层 | 需求 | 实现 |
|---|---|---|
| **能力层** | 理解问题、检索牌义、给出解读 | LLM + RAG |
| **流程层** | 多阶段、有阻塞点、可恢复 | Agent 编排 + 状态机 + 快照 |
| **体验层** | 仪式感、视觉、音频、动效 | 28 个定制组件 + Web Audio 引擎 |
| **工程层** | 可观测、可回归、可部署 | 37 个验证脚本 + SQLite 事件日志 + SSE 事件流 |

## 3. 核心设计决策（10 个，每个含取舍）

### 决策 1：用「确定性状态机」而不是「让 LLM 自由发挥」

**问题**：Agent 的流程如果完全由 LLM 决定，会出现：
- 跳过承约直接抽牌
- 抽了 3 张牌但只解读 1 张就收束
- 无限循环直到撞 max_rounds

**决策**：把占卜拆成 **7 个阶段**（analyze → retrieve → draw → interpret → wait_user → review → done），由 `ritual-machine.ts` 的状态机强制流转；LLM 只在状态机允许的节点上做决策。

**结果**：
- 快速问答模式曾出现"抽完牌不解读就收束"的 bug，根因是 `close_reading` 守卫检查了 `slot.reading`，而快速模式（`perCardGated: false`）**根本不调用 `interpret_card`** → 守卫永远阻塞 → 重试到 max_rounds。修复方式是按模式分支判断（`reveal` vs `reading`）。
- **这类 bug 只有在状态机足够显式时才能被定位** —— 如果流程隐含在 prompt 里，这就是"玄学 bug"。

**代价**：新增阶段要改状态机 + 验证脚本，不是"改个 prompt 就行"。

---

### 决策 2：HITL 用「服务端快照 + 前端表单」，而不是「LLM 等待」

**问题**：LLM 调用是**单向**的。让 LLM "等用户回答"在技术上要么阻塞一个 HTTP 请求（浪费连接、不可恢复），要么轮询（延迟高）。

**决策**：
1. LLM 调 `ask_user` 工具 → Supervisor **结束本次 SSE 流**，把待答状态**写入 SQLite 快照**
2. 前端收到 `ask_user` 事件 → 渲染对应表单（clarify / contract / invocation / card_confirm / flip / crossroads / closing）
3. 用户提交 → `POST /api/answer` → **从快照恢复**到暂停点 → 继续

**关键设计**：
- **阻塞点唯一**：`reveal_card` 是唯一的 `await` 阻塞点（其余环节只发 phase 事件不阻塞）→ 否则前端会残留一堆空 ask 面板
- **快照粒度**：会话状态 + 牌序 + 每张牌的解读槽位 → 恢复后精确知道"该继续哪一步"

**结果**：用户可以在任何一步关掉页面，第二天回来接着占卜。

**代价**：每次恢复都要反序列化快照，状态机复杂度上升。

---

### 决策 3：SSE 事件分 20+ 种类型，而不是一个大 JSON

**问题**：如果 SSE 只推 `{type: "text", content: "..."}`，前端就只能在最后一次性渲染 —— 但占卜过程有"检索命中了哪几张牌"、"翻牌了"、"要你回答"等**结构化事件**。

**决策**：定义 20+ 种事件类型（`session` / `phase` / `reasoning` / `tool` / `rag_hits` / `cards` / `ask_user` / `subagent` / `review` / `delta` / `card_reveal` / `card_reading` / `card_flip_ready` / `contract` / `invocation` / `round` / `plan` / `persona_suggest` / `nudge` / `done` / `error`）。

**特别设计**：
- `cards` 事件**只含位置**，不含 `nameZh`/`image`（**防偷看** —— 牌面在翻转前绝不能下发给前端）
- `card_flip_ready` 不含牌面，`card_reveal` 才下发 → 双保险
- `nudge` 独立于 `phase`：phase 是流程切换（前端切状态条），nudge 只是阶段内的一行轻提示（"第 2 张牌"）→ 语义不同，不能复用

**结果**：前端能把整个 Agent 执行过程**可视化**成时间线（`TraceTimeline.tsx` / `SubAgentPipeline.tsx` / `AgentTrace.tsx`）。

---

### 决策 4：RAG 用「BM25 + 向量 + RRF」三路混合

**问题**：塔罗牌义检索有两个天然矛盾的需求：
- 用户问"我最近感情不稳定" → 需要**语义**匹配（"不稳定" ↔ "动摇"）
- 用户问"权杖三" → 需要**精确**匹配（牌名）

**决策**：三路并行 + RRF（Reciprocal Rank Fusion）融合：

```
BM25 (词法精确)  ┐
向量检索 (语义)   ├→ RRF(k=20) → top-k → 注入 prompt
牌名直查 (精确)  ┘
```

**实现细节**：
- BM25 是**完整实现**（k1=1.5, b=0.75，IDF + 中文 2-gram 切词 + 字段权重 + 每牌去重）
- 中文没有空格 → 用 **2-gram 切词**（"感情不稳定" → "感情/感不/不稳/稳定"）
- 向量检索用 `Xenova/all-MiniLM-L6-v2`（384 维，22MB），**已成功下载并启用**
- 保留特征哈希与纯 BM25 作为**两级降级兜底**

> ⚠️ **一个反直觉的调优点**：RRF 的常数 `k` **本项目用的是 20 而不是教科书上的 60**。
> 原因写在代码注释里：k=60 时 rank 分差被压平，**精确牌名直查通道的优势体现不出来**。
> → 同一个公式，常数不同，效果差很多 —— **参数要按自己的数据调，不能照抄**。

**结果**：融合检索的命中率与相关性都优于单路，且**零外部 API 依赖**。

**代价**：首次启动要下载/加载模型（约 1~2 秒），已做懒加载 + 缓存。

---

### 决策 5：上下文用「滑动窗口 + 分层截断」，而不是简单截断

**问题**：深度解读 3 张牌 + 收束总结，prompt 会累积到几万 token，成本高且稀释注意力。

**决策**（`truncation.ts` + `llm.ts`）：
- **滑动窗口**：只保留最近 N 轮完整对话
- **分层截断**：完整消息 → 截断工具输出 → 摘要更早的历史
- **工具结果特殊处理**：`rag_search` 的返回只保留最相关的片段（工具描述里明确写了"别为每张牌单独调一次"）

**结果**：第二轮优化时**快照写入减半 + 索引 + 错误边界 + prompt 瘦身**共 22 项全部落地（见第 12 章）。

---

### 决策 6：LLM 调用要有「重试 + 降级 + 降级链」

**问题**：外部 API 会超时、限流、返回格式错误。

**决策**（`llm.ts` 976 行 + `fallback.ts` 380 行）：
- **重试**：指数退避 + 抖动（避免惊群）
- **格式错误重试**：把校验错误信息回喂给模型让它自己修（比直接失败好）
- **降级链**：主模型 → 备用模型 → 本地规则（`fallback.ts`）→ 兜底文案
- **记录**：每次调用写 `llm_usage` 表（agent / duration_ms / ok）

**结果**：2026-10-23 曾出现"SSE 流 7.3 分钟无输出"，靠**分段日志 + SQLite 流水**精确定位到"卡在卡片叙事"这一步 —— 工具调用记录**既没有成功也没有失败**，说明卡的不是 LLM 调用本身。

> ⚠️ **这是可观测性价值的最好例证**：没有分层日志 + DB 流水，这个 bug 根本无从查起。

---

### 决策 7：限流与成本控制要「去技术化」

**问题**：技术性错误信息（"429 超出速率限制"）对普通用户是噪音。

**决策**（`verify-ux-fixes.mjs` 断言）：
- 用户看到的是"请求太频繁了，稍后再试"这类**人话**
- 技术细节只写进日志
- 429 / 503 / 超时各有不同话术

---

### 决策 8：视觉系统用「色彩角色规则」而不是「逐页设计」

**问题**：多页面、多组件，如果每个都单独调色，很快就不一致。

**决策**：定死一条规则：

> **背景紫 / 容器深 / 描边金 / 图标金 / 文字白**

并且用 Tailwind 4 的 `@theme` 把令牌做成 CSS 变量。

**特别规则**：
- **禁用 Unicode 符号当图标**（U+2600–U+26FF 全清零）→ 一律用 SVG。`verify-icons.mjs` 断言 emoji 已清零 + 图标名类型有效。
- **占卜师头像 / 魔法阵 / 牌背** 统一到"新艺术风格"（Art Nouveau）—— AI 生成的曼陀罗纹样与手绘感金线纹样是同一套视觉语言。

**结果**：视觉一致性由**断言**保证，而不是靠眼力。

### 决策 9：AI 素材要有「后处理管线」，不能直接用生成结果

**问题**：MiniMax `image-01` 的输出有几个"不能直接用"的问题：
1. 牌背图带**白边**
2. 主体图带**黑底或深蓝底**
3. JPEG 有块状伪影 + 体积大
4. 尺寸固定 1024²（但我们只需要 128~820px）

**决策**：写 `scripts/dev/prep-assets.mjs`（sharp 管线），顺序严格：

```
cropToContent（裁掉四周空白）
  → luminanceAlpha（按亮度映射 alpha，抠掉底色）
  → tint（色相统一成金色系）
  → resize（缩到目标尺寸）
  → circle mask（头像用）
```

**踩过的坑**（详见第 13 章）：
- `cropToContent` 必须在 `luminanceAlpha` **之前** —— 缩放会插值淡化细线，亮度掉到阈值下就丢了
- 包围盒会被**四角噪点**污染 → 只统计中心 80% 区域
- **亮度分不开"深蓝底"和"暗金框线"** → 需要 `cornerFlood`（边缘连通抠底）
- raw buffer 跨进程传递会**丢尺寸元数据** → 必须显式 `.png()`

**结果**：全部素材透明底、体积可控（7KB~148KB）、风格统一。

### 决策 10：环境音用「程序化合成」而不是音频文件

**问题**：市面上的"神秘/冥想/塔罗背景音乐"绝大多数是**有版权的商业曲**或来源不明的 CC 音频。打包进仓库 = 侵权与下架风险。

**决策**：用 **Web Audio API 实时合成**，7 个仪式阶段对应 7 个氛围层。

**为什么这不只是"省体积"**：
| 维度 | 程序化合成 | 音频文件 |
|---|---|---|
| 版权 | ✅ 零风险，版权永远在自己手里 | ❌ 需要采购授权 |
| 体积 | ✅ **0 字节**（代码即音源）| ❌ 3 分钟 MP3 = 3~5MB |
| 随流程变化 | ✅ 换参数即换氛围 | ❌ 做不到 |
| 离线可用 | ✅ | ⚠️ 需要打包 |
| 无限不重复 | ✅ 随机触发 | ❌ 循环几次就腻 |
| 音色品质 | ❌ 合成音偏"电子" | ✅ 真实 |

**代价与应对**：合成音确实更难听 → 用**客观指标**驱动优化（见第 9 章）。

## 4. RAG 检索链路

### 4.1 数据来源与真实性

79 张牌的**真实**塔罗数据（中文牌名、正逆位、原文出处链），源自开源项目 `tarot-lab`（MIT 协议）。

> ⚠️ **这是面试中值得强调的一点**：RAG 的价值不在检索算法本身，而在**语料质量**。
> 如果入库的是编造的内容，再好的检索也只会得到"自信的错误"。

### 4.2 检索管线

```
用户提问
   │
   ├─→ 【BM25 通道】── Okapi BM25 (k1=1.5, b=0.75)
   │                    · IDF
   │                    · 中文 2-gram 切词
   │                    · 字段权重（牌名 > 关键词 > 描述）
   │                    · 每牌去重
   │
   ├─→ 【向量通道】── transformers.js + ONNX
   │                    · Xenova/all-MiniLM-L6-v2 (384 维, 22MB)
   │                    · 特征哈希兜底 + 纯 BM25 二级降级
   │
   └─→ 【牌名直查】── 精确匹配（如"权杖三"）
                            │
                     ┌──────┴──────┐
                     │  RRF(k=60)   │  ← Reciprocal Rank Fusion
                     └──────┬──────┘
                            ↓
                   top-k 片段（带 [n] 编号）
                            ↓
              注入 system prompt（原文片段 + 编号）
                            ↓
                     LLM 生成解读（引用 [n]）
```

### 4.3 RRF 为什么不用加权求和

RRF（Reciprocal Rank Fusion）只看**排名**不看**分数**：

```
score(d) = Σ 1 / (k + rank_i(d))
```

**为什么重要**：BM25 的分数是无界的（可能 0.1 也可能 50），余弦相似度是 [-1,1]。**直接加权求和需要先归一化，而归一化方式会引入巨大偏差**。RRF 天然规避这个问题 —— 这是 IR 领域的标准做法。

**本项目的 k = 20**（不是常见的 60）—— 原因见上文"实现细节"。

### 4.4 检索结果的可追溯性

命中片段注入 prompt 时带编号，模型输出保留引用标记 → 前端 `CitedReading.tsx` 解析引用（`maxCite` 限制条数）并渲染成可点击的引用卡片。

> **设计动机**：塔罗解读本质是"基于文本的推理"，如果用户看不到依据，就只是"AI 在编故事"。**引用让神秘感和可信度并存。**

## 5. 多 Agent 编排与 Supervisor 主循环

### 5.1 两层 Agent 结构

**第一层：子 Agent 管线（Reflexion 模式）** —— `subagents.ts`

```
analyst（分析）→ writer（撰写）→ reviewer（审校）
     ↑                                      │
     └──────── 反馈重写（最多 N 轮）────────┘
```

**为什么拆三个而不是一次调用**：
1. **质量门控**：reviewer 三维打分（`grounding` 依据是否扎实 / `empathy` 共情 / `tone` 语气）→ 不合格就带反馈重写
2. **可观测**：每个子 Agent 的产出都是独立事件（`subagent` SSE 事件）→ 前端 `SubAgentPipeline.tsx` 可视化
3. **关注点分离**：analyst 只管"牌义与推理"（不许写散文）、writer 只管"表达"、reviewer 只管"挑错"

**第二层：Supervisor 主循环 + 12 个工具** —— `supervisor.ts` + `tools/definitions.ts`

| 工具 | 作用 |
|---|---|
| `rag_search` | 混合检索牌义知识库 |
| `draw_cards` | 抽牌（three / single）|
| `offer_card_selection` | 展开牌阵，请用户自己翻 |
| `reveal_card` | **唯一的阻塞 await 点**（翻牌）|
| `establish_contract` | 承约：复述问题 + 界定范围 |
| `invoke_three_questions` | 呼召三问 |
| `ask_user` | 通用提问 |
| `fate_crossroads` | 岔路口 |
| `interpret_card` | 逐张解读 |
| `interpret_all_cards` | 批量解读 |
| `write_reading` | 写入解读槽位 |
| `close_reading` | 收束 |

**工具白名单是硬约束**：不同阶段只向 LLM 提供该阶段该用的工具 schema，**不是靠 prompt 说"你只能调用 X"，而是根本不提供其他工具**。

> ⚠️ **为什么这重要**：LLM 会调用它"看到"的任何工具。靠 prompt 约束 = 靠自觉；靠 schema 约束 = 靠机制。
> 这也解释了为什么 `close_reading` 的守卫 bug（快速模式下 `interpret_card` 根本不执行）能造成死锁 —— **工具集与状态机必须成对设计**。

### 5.2 Supervisor 主循环

```
while (round < maxRounds) {
  ① 检查阻塞点        → 有 ask_user 就结束流、存快照、返回
  ② 推进状态机        → 决定当前阶段的合法动作
  ③ 组装 prompt        → 系统提示 + 滑动窗口 + 工具结果 + 牌面状态
  ④ 调用 LLM           → 重试/降级链（llm.ts）
  ⑤ 解析工具调用        → Zod 校验
  ⑥ 执行工具            → RAG / 抽牌 / 提问
  ⑦ 广播 SSE 事件       → 让前端实时看到
  ⑧ 记录快照 + 事件日志  → 可恢复 + 可观测
}
```

### 5.3 阶段状态机

```
analyze ──→ retrieve ──→ draw ──→ interpret ──→ wait_user
                          ↑                        │
                          └────（还有牌没翻）──────┘
                                                    ↓
                                                  review ──→ done
```

**`ritual-machine.ts` 显式声明**每个阶段允许哪些动作、每个动作的前置条件。

### 5.4 上下文管理

| 策略 | 作用 |
|---|---|
| 滑动窗口 | 只保留最近 N 轮完整对话 |
| 分层截断 | 完整消息 → 截断工具输出 → 摘要更早历史 |
| 工具结果瘦身 | `rag_search` 只返回最相关片段（tool description 里明确要求合并查询）|
| 快照瘦身 | 第二轮优化：快照写入量减半 |

## 7. SSE 流式协议设计

### 7.1 为什么是 SSE 而不是 WebSocket

| | SSE | WebSocket |
|---|---|---|
| 方向 | 单向（服务器→客户端）✅ | 双向 |
| HTTP 兼容 | ✅ 走标准 HTTP | ❌ 需要 Upgrade |
| 自动重连 | ✅ 浏览器原生 | ❌ 要自己实现 |
| 代理/CDN 友好 | ✅ | ⚠️ 经常要特殊配置 |

占卜是"服务器推送为主，用户回答走独立 POST" → **SSE 天然够用**。

### 7.2 事件协议

**20+ 种事件类型**，每个都是**语义化**的而不是"文本块"：

```
session      → 会话建立
phase        → 阶段切换（前端切状态条）
reasoning    → LLM 思考摘要
tool         → 工具调用（rag_search / draw_cards …）
rag_hits     → 检索命中的牌（含相似度）
cards        → 牌阵位置（★ 不含牌名，防止偷看）
card_flip_ready → 某张牌可以翻了（★ 不含牌面）
card_reveal  → 翻牌结果（★ 此时才下发牌面）
card_reading → 该牌解读完成
ask_user     → 需要用户输入
subagent     → 子 Agent 状态
review       → 审校结果
delta        → 增量文本
contract/invocation/round/plan → 仪式节点
nudge        → 阶段内轻提示（≠ phase）
done / error
```

### 7.3 防偷看的双保险

**问题**：如果前端能在翻牌前拿到牌面，整个"仪式感"就没了 —— 用户会想"系统是不是早就决定好了"。

**决策**：
1. `cards` 事件只发 `{ position }`，牌名/图片字段留空
2. `card_flip_ready` 不含牌面
3. `card_reveal` 才下发完整牌面

**三层保险**（数据层 + 协议层 + 渲染层）。

## 9. 程序化音频引擎

### 9.1 为什么值得单独讲

这是本项目里**最能体现"用数据驱动解决审美问题"**的一段。

**背景**：用户三次反馈环境音难听：
1. 「目前只是单纯的沙沙声」
2. 「还是很长很长的空鸣声，特别刺耳」
3. 「现在很难听」

三轮反馈指向完全不同的病因，说明**光靠主观迭代无法收敛**。

### 9.2 把审美问题变成数据问题

**工具**：`scripts/dev/render-ambience.mjs`
- 无头 Chrome + `OfflineAudioContext` **离线渲染 12 秒真实波形**
- 在页面内做 **FFT 频谱分析**（自己写的基 2 FFT，因为不想为 dev 工具装依赖）
- 导出 WAV 供人耳试听

**四个客观指标**：

| 指标 | 含义 | 甜区 |
|---|---|---|
| **频谱重心** | 声音的平均"亮度" | 300~1200Hz（>2000 = 刺耳）|
| **低频能量占比** | 有没有"重量" | > 8% |
| **高频能量占比** | 会不会刺耳 | < 5% |
| **RMS 变异系数** | 有没有呼吸感 | > 0.15 |

### 9.3 改造前后的对比

| 层 | 频谱重心 | 低频 | 中频 | 高频 | RMS 波动 |
|---|---|---|---|---|---|
| idle | 430Hz | 47% | 52% | 0.2% | 0.24 |
| contract | 334Hz | 48% | 52% | 0.2% | 0.24 |
| invocation | 497Hz | 30% | 69% | 0.9% | 0.27 |
| selection | 396Hz | 55% | 45% | 0.2% | 0.23 |
| perCard | 458Hz | 42% | 57% | 0.8% | 0.23 |
| synthesis | 541Hz | 22% | 77% | 0.6% | 0.29 |
| closing | 364Hz | 43% | 56% | 0.5% | 0.24 |

**改造前**（旧版只有噪声底床 + 正弦点音）：
- 频谱重心高（刺耳）
- 低频 ~1.5%（声音"薄、飘、无重量"）
- 8 拍后原地重复（催眠/烦躁）

### 9.4 补上的五个要素（真实音乐的四要素 + 质感）

#### ① sub-bass（低频基础）
A1~A2（55~110Hz）· 低通 140Hz（只留基频）· 0.05Hz LFO 幅度调制（呼吸）

**⚠️ 这里有一个极其隐蔽的 bug，也是本项目最有教学价值的案例：**

旧 `noteToFreq` 的实现是：
```ts
const oct = (isLow ? -1 : 0) + octaveOffset;
return base * Math.pow(2, oct);
```
→ `noteToFreq("A1")` = 440 × 2⁻¹ = **220Hz**

而 **220Hz 落在人耳最敏感的频段** → 持续播放 = 耳鸣感 = 刺耳。

> ⚠️ **这正是三个月前用户投诉"很长很长的空鸣声"的根因 —— 被我"修"进了新的 sub-bass 层。**

修正用标准公式 `base × 2^(octave - 4)` → A1 = 55Hz。

> 💡 **提炼出的判断标准**（可以背下来）：
> **持续音是"听到"还是"感到"？**
> - 听到 → 危险（220Hz~1kHz 是听觉系统当"测试信号"的区间）
> - 感到 → 安全（40~110Hz 是胸腔物理震动区，人耳几乎不"听"到基频）

#### ② super-saw（厚度）
```ts
const SAW_VOICES = [0, 7, -7, 14, -14];  // cents
```
5 个失谐正弦叠加 → 宽谱无拍频。
- < 3 cents：听不出宽度
- 3~5 cents：轻微拍频（"颤"）
- **5~15 cents：宽谱、暖、无拍频** ✅
- > 20 cents："合唱失调" → 脏

#### ③ LFO 低通扫描（呼吸感）
0.033~0.085Hz 扫描 ±300~620Hz。

**⚠️ 关键约束**：LFO **只接 `filter.frequency`，绝不接音量**。
接音量 = 强弱起伏的空鸣（正是要避免的）；接截止频率 = 音色开合的呼吸感。

#### ④ 和声轮换（和声进行）
每层 4 个和弦轮换：
```
idle:       Am → F → C → G        （最经典的循环，温暖流动）
contract:   Am → Dm → E7 → Am      （i→iv→V→i，有"走向"感）
invocation: Am → Em → F → C        （i→v→VI→III，悬而未决 → 神秘）
selection:  Dm → Am → Bb → Gm      （ii→v→VI→iv，不安定的悬着）
perCard:    C → G/B → Am → F       （IV→I/iii→vi→ii，温柔的循环）
synthesis:  Am → F → C → E         （回到最经典但更亮）
closing:    Am → Dm → E → Am       （回到主音，安放）
```
6~13 秒换一个 → 解决"8 拍后原地重复"。

#### ⑤ FM 钟琴（质感）
- 载波/调制器比 = **√2**（无理数 → 泛音落在**非谐波**位置 → 金属质感 = 磬）
  - 比值是整数 → 泛音落在谐波上 → 声音"纯"、像风琴
- 音高取**大调五声**（C D E G A，无半音/三全音 → 随机触发也不冲突）
- 间隔随机抖动 ±35%（打破机械感）

### 9.5 混响 IR 重做

原 IR = 纯指数衰减噪声 → 听起来是"**糊的雾**"。

真实房间混响有两阶段：
1. **早期反射**（0~80ms，稀疏脉冲）→ 人脑靠它判断"房间多大、墙有多远" → **没有它 = 没有空间感，只有糊**
2. **扩散尾**（80ms+）→ 体积感

现在两者都有，且左右声道延迟**错开 3~7ms** → 声场展开（左右完全相同 = 声音贴在正前方一个点上）。

### 9.6 噪声底床修复
- 音量 0.004 → 0.008~0.011（原来几乎听不见，**形同虚设**）
- **新增高通 140Hz**（切掉低频隆隆声，与 sub-bass 不打架）

### 9.7 防止"审美退化"的工程手段

**`scripts/verify-ambience-tone.mjs`（45 条断言，已接入 CI）**

> ⚠️ **为什么审美问题需要断言**：
> 审美问题不报错，只是"听着难受"。而且下一个人重构时，很容易觉得"这些层是历史包袱"就删掉。
> → 用断言把"设计契约"钉死：每条断言对应一个具体的听感问题。

它同时守住"消除空鸣"的既有修复不被回退（正弦而非三角波、拨弦式包络、音效尾巴 ≤1.5s、混响量 ≤0.5）。

## 11. 可观测性与工程化

### 11.1 为什么这类系统特别需要可观测性

AI Agent 系统有一个特殊困难：**失败点不明显**。
- 传统后端：报错 = 500 日志
- Agent：可能"成功返回了但内容是空的"、"无限重试"、"卡在某个语义步骤"

本项目的三层可观测性：

| 层 | 实现 | 解决什么 |
|---|---|---|
| **SSE 事件流** | 20+ 事件类型实时广播 | 前端能显示"现在在干什么" |
| **SQLite 事件日志** | `event_log` 表记录每个事件 | 事后能回放完整执行路径 |
| **LLM 用量表** | `llm_usage`（agent / duration_ms / ok）| 定位"是 LLM 慢"还是"业务逻辑慢" |

**真实案例**：2026-10-23 "SSE 7.3 分钟无输出"。
- 步骤 1：服务端日志 → `POST /api/interpret 200 in 7.3min`，确认不是框架层
- 步骤 2：查 SQLite → `llm_usage` 里 supervisor 调用**全是 OK**，但**没有成功也没有失败**
- 步骤 3：查 `tool_calls` → 只有 2 条（`ask_user`、`offer_card_selection`）
- **结论**：卡的不是 LLM 调用本身 → 是"卡片叙事"这一步的逻辑

> ⚠️ **这就是分层日志 + DB 流水的价值**：没有它们，这个 bug 根本无从查起。

### 11.2 671 条断言

37 个验证脚本，每个断言一个**具体的技术契约**：

| 类别 | 脚本 | 断言数 |
|---|---|---|
| Agent 协议 | `verify-ritual-machine` / `verify-phase-guard` / `verify-fallback-parity` | 状态机、降级一致性 |
| HITL | `verify-hitl-nudge` / `verify-resume-trigger` | 阻塞点唯一性、快照恢复 |
| 稳定性 | `verify-rate-limiter` / `verify-rate-concurrency` / `verify-sse-cancel` | 限流、并发、SSE 取消 |
| 数据 | `verify-runtime-state` / `verify-telemetry-buffer` / `verify-optimization-goals` | 运行时状态、遥测缓冲 |
| 体验 | `verify-ux-fixes` / `verify-icons` / `verify-round2` | UX 修复、图标规范、优化项落地 |
| 业务 | `verify-divination-mode` / `verify-quick-mode` / `verify-fortune` / `verify-oracle` | 双模式、快速问答、运势矩阵、问神谕 |
| 视觉/音频 | `verify-ambience` / `verify-ambience-tone` | 环境音映射、**音色质量** |

**断言的对象是"契约"不是"文件存在"**。例如：

```js
// ❌ 弱断言：文件在就行
check("ambient.ts 存在", existsSync("src/lib/audio/ambient.ts"));

// ✅ 强断言：设计契约没被破坏
check("乐句仍用正弦（不是三角波 → 无长笛感）",
  !/osc\.type = "triangle"/.test(arpFn[0]));
check("音效尾巴仍短（磬/锣 ≤1.5s）",
  /now \+ 1\.2/.test(code) && !/now \+ 2\.4/.test(code));
```

## 13. 踩坑复盘（12 个真实 bug）

> 面试讲 bug 比讲架构更有说服力 —— 它证明你**真的在做**，而且**真的在解决问题**。

### Bug 1：神谕回复发两遍
- **现象**：问神谕页面，AI 回复出现两次
- **根因**：SSE 事件订阅与重连逻辑重复订阅
- **修复**（`306f616`）：订阅去重

### Bug 2：快速问答撞 max_rounds
- **现象**：走完抽牌流程后，又走一遍抽牌，翻不过图，报"达到最大轮次"
- **根因**：`close_reading` 守卫检查 `slot.reading`，但快速模式 `perCardGated: false` **根本不调用 `interpret_card`** → 守卫永远阻塞 → 重试到 max_rounds
- **修复**（`f0de3fd`）：按模式分支（`reveal` vs `reading`）+ narrative 兜底
- **验证**（`6b39f95`）：端到端断言 `draw_cards ≤ 1`、3 次 `card_reveal`、到达 closing

### Bug 3：素材处理输出"横条纹"
- **现象**：三个入口图标全变成横条纹
- **根因**：esbuild 的 raw pipeline `toBuffer()` **不携带尺寸元数据** → 下游 `sharp(buffer)` 无法推断宽高 → 输出乱码
- **修复**：extend 后**显式 `.png()`** 再 toBuffer
- **附带发现**：裁剪结果**必须写回 `img`**，否则 `resize()` 缩放的是原始未裁剪的实例

### Bug 4：图标"四个边角白底"
- **现象**：用户明确指出"今日之牌的图标外面还有白色的底色，周围没有透明化完全，还有四个边角"
- **根因**：该图标构图是「**黑圆 + 米白方块背景**」→ 四角亮度 250+（比金线还亮）→ 任何亮度阈值都分不开
- **修复**：**边缘连通抠底**（`cornerFlood`）—— 用**连通性**而非亮度区分
  - 从四角 + 四边做 BFS（4 邻域，避免沿对角线漏进黑圆缝隙）
  - 与角连通且亮度 > 阈值 → 判为背景
  - 金色线被黑圆包住，与边缘不连通 → 完整保留

### Bug 5：环境音"很难听"
- **见第 9 章**（本项目最有价值的案例）

### Bug 6：AI 图标不可见（1KB）
- **根因**：三个连续的问题
  1. `cropToContent` 跑在 resize **之后** → 坐标系错位
  2. `luminanceAlpha` 跑在 resize **之后** → 插值淡化细线，亮度掉到阈值下
  3. `cropToContent` 配置根本没加进去（PowerShell 替换在 CRLF 上静默失败）
- **修复**：调整顺序 + 验证 `Select-String` 替换结果

### Bug 7：按钮"框比图片大，里面是黑底"
- **根因**：AI 出的金框图是 16:9，按钮约 3:1 → 拉伸变形；中间是深蓝底 → 抠不干净
- **修复**：**放弃 AI 图，改纯 CSS 三层渐变模拟金属**（斜向高光带 + 底部暗带 + 顶部亮线）

### Bug 8：PPR + `new Date()` 的四连坑
Next.js 16 的 `cacheComponents: true`（PPR）下：
1. `new Date()` 需要 `await connection()`
2. `redirect()` 运行时 → 必须包在 `<Suspense>` 里
3. Suspense `fallback` 里不能有 `new Date()`
4. 客户端组件也不能用 `new Date()`

### Bug 9：Flexbox 陷阱
`<main className="flex flex-col items-center">` 会**收缩**绝对定位子元素的交叉轴尺寸 → 背景层需要显式 `w-full`

### Bug 10：CSS 动画类复用陷阱
旧的 `spin-slow` keyframes 里含 `translate(-50%,-50%)` → 新的 `astral-spin*` 类不能复用（会偏移）

### Bug 11：`mix-blend-mode: screen` 不生效
父元素有 `opacity`/`filter`/`transform` → **新建层叠上下文** → screen 只在元素内部生效，不会与父背景融合。
→ **解决：把透明度烘进素材本身**（sharp alpha），而不是靠 CSS blend。

### Bug 12：PowerShell 字符串替换的连锁伤害
- `-replace` 在 CRLF 文件上**静默失败**
- 中文弯引号破坏 `-e`/heredoc 解析
- 块替换导致重复 `/**` → `{` 变成注释的一部分 → **任务被静默跳过**
- **教训**：写脚本文件而不是内联命令；每次替换后 `Select-String` 验证

## 14. 项目优点（可量化的）

### 14.1 架构优点

| 优点 | 具体体现 |
|---|---|
| **状态机显式化** | 7 阶段 + 21 事件类型，流程不隐含在 prompt 里 |
| **防偷看三层保险** | 数据层（牌面字段留空）+ 协议层（reveal 才下发）+ 渲染层 |
| **可恢复性** | 任何步骤断线 → 快照恢复 → 精确续上 |
| **零外部音频依赖** | 环境音 0 字节，版权永远在自己手里 |
| **零外部向量 API** | 本地 ONNX embedding |

### 14.2 工程优点

| 指标 | 数值 |
|---|---|
| 验证断言 | **671 条 / 37 个脚本** |
| 代码规模 | src 21,468 行 · scripts 10,425 行 |
| 断言与代码比 | **~3.1%**（每 32 行代码配 1 条断言）|
| TypeScript | `strict` + `tsc --noEmit` 0 error |
| ESLint | 0 error |
| 提交粒度 | 103 个提交，每个聚焦单一变更 |

### 14.3 最值得强调的三点

**① 状态机让"玄学 bug"变成可定位的 bug**
快速问答的 max_rounds 问题，根因是"守卫检查的字段在某种模式下根本不会被写入"。这种 bug 如果流程隐含在 prompt 里，**永远查不出来**。

**② 把审美问题变成数据问题**
环境音的三轮反馈（沙沙声 → 空鸣 → 很难听）指向三个不同病因。做法不是"再调调看"，而是：
- 建**离线渲染 + FFT 频谱分析**的工具
- 定出**四个客观指标**和甜区
- 用数据定位到那个隐蔽的八度 bug

**③ 版权与体积的架构级决策**
环境音选程序化合成而非音频文件，**不是省事**，而是在架构层面解决了版权风险（PWA 要预缓存、3 分钟 MP3 = 5MB）+ 无限不重复 + 随阶段变化。代价是音色更难听 → 用数据驱动补回来。

## 16. 面试高频问答准备

### Q1：为什么用 Next.js 而不是纯后端 + React SPA？

**答**：因为这个产品**有一半是 SEO 需求**（每日之牌、运势矩阵、分享卡）。运势页是"任何人任何时间都可能搜到的内容"，SSR 是刚需。同时 Next.js 让 SSE API 路由和前端同仓，避免 CORS、部署单元拆分、类型共享三件事。

### Q2：SSE 断线了怎么办？

**答**：三条防线：
1. 浏览器原生自动重连（`EventSource`）
2. 会话状态在 SQLite 快照里 → 重连后 `GET /api/session/[id]` 恢复
3. 前端有"重连中"提示，用户可以手动重试

关键设计：**恢复靠快照，不靠连接**。

### Q3：怎么保证 LLM 不乱来？

**答**：四层约束：
1. **状态机**：阶段决定允许的动作
2. **工具白名单**：每个 Agent 的 schema 里只有它该用的工具（不是靠 prompt 说）
3. **Zod 校验**：LLM 输出必须结构化合法，非法则回喂错误让它自己修
4. **降级链**：LLM 挂了还有规则引擎兜底

### Q4：为什么不用 LangChain / LlamaIndex？

**答**：三个理由：
1. **控制力**：状态机是显式代码，不是 prompt 里的一句话
2. **依赖体积**：我们的 RAG 只需要 BM25 + 向量 + RRF，自己实现反而更可控（还要处理中文 2-gram 切词这种细节）
3. **可观测**：我们自己写的链路能精确记录每一步，框架的内部调用反而是黑盒

代价：自己实现了重试、降级、schema 等基础设施（约 2000 行）。**如果需求更通用，框架更划算。**

### Q5：RAG 效果怎么评估？

**答**：目前靠 `eval-rag.mjs` 做检索层评估（命中率/相关性）。**坦白说**：LLM 生成层的评估还不够自动化 —— 主要是人工看 + 断言结构性指标（引用编号是否存在、是否幻觉牌名）。

### Q6：并发/限流怎么做？

**答**：三层：
1. **IP 级令牌桶**（`verify-rate-limiter` / `verify-rate-concurrency`）
2. **会话级**（同一会话的并发请求排队）
3. **上游 API 429** → 指数退避重试 + 用户侧去技术化话术

### Q7：成本怎么控制？

**答**：
- **上下文管理**：滑动窗口 + 分层截断 + 工具结果瘦身
- **RAG 合并查询**：tool description 明确要求"别为每张牌单独调一次"（避免 N 倍 token）
- **快照瘦身**：第二轮优化写入量减半
- **降级链**：主模型失败时先降级再重试，避免无限重试烧钱
- **用量表**：每次调用记录 agent/duration/ok，可分析成本

### Q8：这个项目最大的技术难点是什么？

**答**：不是某个技术点，而是**"把不可控的 LLM 行为约束成可预期流程"**。

具体体现：
- 快速问答的 max_rounds 死锁 —— 根因是状态守卫与执行路径的模式不一致
- 防偷看 —— 要同时在数据、协议、渲染三层堵
- 快照恢复 —— 要精确知道"该从哪一步继续"

### Q9：如果重做一遍，你会改什么？

**答**（这是个好问题，诚实回答比吹嘘好）：
1. **更早建客观指标**：环境音应该在第一版就有频谱分析工具，而不是三轮反馈后才建
2. **端到端测试更早**：脚本级验证覆盖了协议，但 UI 交互的回归（比如按钮 hover 态）只能靠人眼
3. **视觉素材用 SVG 优先**：AI 生成适合"氛围图"，不适合"需要精确控制的 UI 元素"（按钮、图标）
4. **状态机用形式化描述**：现在是代码里的 switch，如果用状态图 DSL，能自动生成 UI 和验证

        │    ⑦ SSE 广播                              │
        │    ⑧ 快照 + 事件日志                       │
        └───────────────┬────────────────────────────┘

        ┌───────────────┼───────────────┬──────────────┐

                   +RRF)                            +事件日志)
        │               │               │              │
        └───────────────┴───────────────┴──────────────┘
                             ↓
                    SSE 事件流（20+ 类型）
                             ↓
        ┌────────────────────────────────────────────┐
        │  前端 28 个组件                              │
        │  · 牌阵/牌面（3D 倾斜、防偷看）              │
        │  · Agent 轨迹（工具/子Agent/思考）          │
        │  · 环境音（阶段联动）                        │
        │  · 背景（8 层 + 动态星云）                   │
        └────────────────────────────────────────────┘
                             ↓
              HITL 阻塞点 → 存快照 → SSE 结束
                             ↓
              用户提交 → POST /api/answer
                             ↓
              读快照 → 恢复 → 继续主循环
