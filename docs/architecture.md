## 一、产品定位与核心矛盾

### 1.1 产品是什么

一个**会走完完整仪式的 AI 塔罗师**。

不是"输入问题 → 随机抽三张牌 → LLM 写一段解读"。区别在于：
真实占卜师会**先复述你的问题让你确认**（承约）、**问三个问题**（呼召）、
**让你亲手挑牌**、**一张一张翻、一张一张讲**、**最后收束**。

这个"仪式"就是产品与通用 LLM 之间的全部差异点。

### 1.2 核心矛盾

产品价值全部押在"仪式感"上，但**LLM 是概率性的**：

| 产品要求 | LLM 的现实 |
|---|---|
| 必须先承约再抽牌 | 它可能直接调 `draw_cards` |
| 必须一张一张讲 | 它可能讲完第一张就直接综合 |
| 每一步都要等用户 | 它可能一口气输出所有内容 |

**核心矛盾：仪式是确定性的，模型是概率性的。**

### 1.3 由此推出的三条设计原则

> 这三条原则贯穿整个代码库，是所有技术选择的依据。

**原则一：凡是产品核心不变量，必须在后端强制，不能靠 prompt 约束。**

```
❌ 靠 prompt："仪式流程…顺序不可颠倒，真实占卜师绝不会跳过这一步"
✅ 靠代码：state machine 的转移表 + 守卫拦截 + 打回提示
```

实测证据：glm-5.3 在 prompt 已明确禁止的情况下，仍有 **32/34 条**评估用例跳过了承约。
prompt 是**软约束**（尽力而为），代码才是**硬约束**（必然生效）。

**原则二：降级不是删减。**

模型不可用时，产品仍要能跑完整场占卜 —— 走本地剧本引擎。
这不只是"别白屏"，而是"仪式感不能因为模型挂了而消失"。

**原则三：指标本身要被验证。**

一个"看起来在工作"的验证脚本，如果判定写错，它给出的绿灯是**假的** ——
比没有验证更危险。

真实案例：`verify-ritual-guard.mjs` 的收束判定写成
`has("ask_user") && ev.includes("ask_user")`（恒等于前者），
而承约/呼召/选牌/翻牌**全都是 ask_user 事件** ——
这个"收束检测"从来没真正检查过收束。

**原则四：外部系统的语义必须实测，不能假设。**

上游配额、网关的流式行为、模型的工具调用习惯 ——
这些都不是"文档里写了什么"，而是**实测出来的**。

真实案例一：第一版限流器用令牌桶（"空闲攒额度"语义），
而上游是「滚动 60 秒内 4 次」（滚动窗口语义）——
两种语义不对等，攒额度后连发就撞墙，实测每场占卜必挂 429。
改成滑动窗口后全程零 429。

真实案例二：用 PowerShell 的 `Invoke-WebRequest` 测 MiniMax 得到
"基础连接已经关闭"，据此写下"这台机器没有公网出口" —— **这是错的**。
改用 Node 的 `fetch`（生产实际使用的运行时）重测：
`MiniMax ✅ 200 (1753ms)`。
.NET 的 HttpClient 与 undici 在 TLS/代理/HTTP2 上行为不同 ——
**实测必须用与生产相同的运行时**，否则结论不可信。

**推论一**：任何"限流/重试/超时"的参数都该有配套的探针脚本，
换环境时能重新测，而不是靠记忆猜一个数。

**推论二**：探针脚本本身也要用对运行时 ——
`scripts/probe-provider-reachability.mjs` 用 Node fetch，
`scripts/probe-gateway-quota.mjs` 直接打网关，两者都与应用同一套网络栈。

### 为什么这样分层

| 分层 | 职责 | 关键约束 |
|---|---|---|
| API 层 | 协议转换（SSE ↔ 生成器） | 不含业务逻辑 |
| supervisor | **只做编排**，不做实现 | 工具/子 Agent/HITL 都委托出去 |
| 领域模块 | 每个模块单一职责，可独立测试 | 状态机、命中率、限流都是可单测的纯逻辑 |

**为什么 supervisor 不许自己实现工具？**
因为它有 1400+ 行。如果 RAG 逻辑、抽牌逻辑、LLM 逻辑都塞进来，
改任何一个都要通读全文；拆出去之后，改限流只需看 `llm.ts` 一个文件。

## 三、一次占卜的完整流程

### 3.1 时序（真实 LLM，glm-5.3）

```
用户：「下周面试能通过吗，我很紧张」
  │
  ├─ POST /api/interpret → 建立会话 → SSE 流开始
  │
  │  ┌ 承约（contract）────────────────────────────────────┐
  │  │ 模型调 establish_contract → 后端 yield contract 事件  │
  │  │ → HITL 闸门就绪 → yield ask_user(contract)          │
  │  │ → 用户确认「对，就是这个」                          │
  │  │ → 阶段推进：contract → invocation                  │
  │  └──────────────────────────────────────────────────────┘
  │
  │  ┌ 呼召（invocation）──────────────────────────────────┐
  │  │ 模型调 invoke_three_questions → 三问                │
  │  │ → 用户回答三个问题（骨架，后续解读的依据）          │
  │  │ → 阶段推进：invocation → card_selection            │
  │  └──────────────────────────────────────────────────────┘
  │
  │  ┌ 选牌（card_selection）──────────────────────────────┐
  │  │ 模型调 offer_card_selection → 扇面 7 张牌背展开      │
  │  │ → 用户亲手点 3 张（记录顺序 + 每张犹豫时长 ms）      │
  │  │ → 阶段推进：card_selection → per_card              │
  │  └──────────────────────────────────────────────────────┘
  │
  │  ┌ 逐张解读（per_card）×3──────────────────────────────┐
  │  │ reveal_card(0) → 翻牌闸门 → 用户点击 → 念牌         │
  │  │   → 确认问题 → 用户回答 → interpret_card(0) 讲透    │
  │  │ reveal_card(1) → …（重复）                          │
  │  │ reveal_card(2) → …（重复）                          │
  │  └──────────────────────────────────────────────────────┘
  │
  │  ┌ 综合（synthesis）───────────────────────────────────┐
  │  │ write_reading → 三子 Agent 管线：                   │
  │  │   analyst(≤250字结构化笔记)                         │
  │  │     → writer(流式撰写，逐字推送)                     │
  │  │     → reviewer(三维度打分 + 修改指令)                │
  │  │        └ 不过 → revision → writer 重写 → 复检      │
  │  └──────────────────────────────────────────────────────┘
  │
  │  ┌ 收束（closing）─────────────────────────────────────┐
  │  │ close_reading → 收尾语 + 一条行动建议 + 收尾追问     │
  │  │ → 用户回答 → 落库 → done                            │
  │  └──────────────────────────────────────────────────────┘
  │
  └─ 情绪人格建议 → 分享（PNG / 链接）→ 可继续追问
```

### 3.2 关键设计：为什么每一步都要"停下来等用户"

看起来很啰嗦，但这是产品的核心：

| 步骤 | 如果省掉会怎样 |
|---|---|
| 承约 | 用户问「我的运势怎么样」，模型自己收敛成一个泛泛的问题 → 解读不对症 |
| 呼召 | 缺失"用户真正想知道什么" → 解读变成通用鸡汤 |
| 选牌 | 丢失仪式感；且**犹豫时长**是解读的素材（"你在恋人牌前停留最久"） |
| 逐张翻牌 | 一次性输出三张牌 = 没有"逐张揭示"的叙事张力 |

**代价**：一场占卜要 9 次用户交互、约 5 分钟（受限于网关限速）。
**收益**：这是"占卜"而不是"生成一段文字"。

## 四、模块逐个解析

### 4.1 Supervisor 编排中枢

**文件**：`src/lib/agent/supervisor.ts`（约 1460 行）

#### 它做什么

ReAct 循环：模型决策 → 执行工具 → 回填结果 → 继续。
外加一层"仪式编排"：保证工具调用顺序符合仪式。

#### 关键实现：单工具/轮守卫

```ts
while (round < MAX_ROUNDS) {
  flushPendingToolResponses();   // ① 补齐上一轮跳过的 tool_call 响应
  flushPendingUserNotes();        // ② 插入暂存的插话
  ...
  decision = await callLLM(...);  // ③ 模型决策（可能返回多个 tool_calls）
  // ④ 只执行第一个，其余补 deferred 响应
}
```

**为什么单工具/轮？**
模型的 `tool_calls` 数组可能一次返回 3 个调用。若全执行，
`establish_contract`（要等用户确认）与 `draw_cards`（立即执行）
就会并发 —— 用户还没确认问题，牌已经抽好了，仪式全乱。

**为什么必须"补齐 deferred 响应"？**
MiniMax 严格协议：assistant 的 `tool_calls` 必须与后续的 `tool` 消息**一一配对**。
少一个 → 下次请求直接 400 `tool call result does not follow tool call`。
这是实测踩过的坑（见 `flushPendingToolResponses` 的注释）。

#### 关键实现：闸门先就绪、再通知

```ts
const flipWait = waitUserAnswer(session, flipPrompt, undefined, "flip", hitlClock);
yield { type: "ask_user", ask: { ... kind: "flip" } };
const flipResult = await flipWait;
```

**为什么顺序不能反？**
`waitUserAnswer` 在 **await 表达式求值时**才设置 `session.pendingAsk`。
若先 yield 事件，客户端收到"可点"信号后立刻 POST `/api/answer`，
但后端还没进入等待 → `pendingAsk` 为空 → **409「当前没有等待回答的问题」** → 应答被丢弃。

**症状极具迷惑性**：界面上牌点不动（409 被吞），而顶部时间线的牌因为用户"看了一会儿才点"反而能翻。

**这个 bug 波及全部 6 处 HITL**（承约/呼召/选牌/确认/收束/翻牌），
2026-11 一次性全部修复（`9bc4ae1`）。

#### 关键实现：看门狗用"活跃时间"口径

```ts
const ACTIVE_BUDGET_MS = Number(process.env.SESSION_DEADLINE_MS) || 8 * 60 * 1000;
// hitlClock.pause() 进入等待时暂停计时，resume() 恢复
```

**为什么不用总时长？**
9 次交互，用户每次思考 1 分钟就是 9 分钟 —— 用总时长会把慢用户的最后一步活活掐死。
"活跃时间"只累计 Agent 真正工作的时间（LLM 调用 + 工具执行）。

### 4.2 仪式状态机（显式转移表）

**文件**：`src/lib/agent/ritual-machine.ts`

#### 解决的问题

改造前，仪式进度靠**隐式判断**：

```ts
if (!session.contractQuestion)            → 还没承约
if (!session.invocation?.answers?.length) → 还没呼召
if (session.drawnCards.length === 0)      → 还没抽牌
```

三个具体危害：
1. **逻辑重复** —— 同样的守卫在 `offer_card_selection` 和 `draw_cards` 各写一遍（共 4 处），改一处忘另一处就漏防
2. **状态不可见** —— dashboard 不知道这场卡在哪一步
3. **无法穷举** —— 合法转移没被显式描述 → 写不了状态机测试

#### 设计

```ts
type RitualPhase =
  | "contract" | "invocation" | "card_selection"
  | "per_card" | "synthesis" | "closing" | "done";

const ALLOWED_TRANSITIONS: Record<RitualPhase, RitualPhase[]> = {
  contract:       ["contract", "invocation"],
  invocation:     ["invocation", "contract", "card_selection"],  // 可回退重做承约
  card_selection: ["card_selection", "contract", "invocation", "per_card"],
  per_card:       ["per_card", "card_selection", "synthesis"],
  synthesis:      ["synthesis", "closing"],
  closing:        ["closing", "done"],
  done:           ["done"],
};
```

**为什么不用 xstate 之类的库？**
这里的"状态"是业务流程进度，转移基本线性（偶尔回退）。
引入库要付出学习成本 + 序列化负担，而一张 30 行的转移表足够，且更好读。

#### 踩过的坑：守卫的语义

第一版守卫只传"当前阶段"，结果**提示指错了阶段**：
承约没定稿就想抽牌 → 提示说"缺呼召"（实际缺的是承约）。

**根因**：`current = "contract"` 有两种含义 —— "承约正在做" vs "承约刚做完"。
光看 current 无法区分。

**解法**：守卫需要两个信息 —— `current`（当前在做什么）+ `completed`（哪些已完成）：

```ts
canEnter(current, target, completedPhases(session), { toolName })
//                        ↑ 统一推导"什么算完成"，与 derivePhase 共用同一套判据
```

#### 向后兼容

老会话快照没有 `ritualPhase` → `derivePhase()` 从已有字段反推。
**不能默认 "contract"** —— 否则恢复一个已承约的会话会被守卫拦住，
用户看到"请先承约"，而它明明已经承约过了。

### 4.3 HITL 人机协同

**文件**：`src/lib/agent/hitl.ts`

#### 唯一阻塞点

整个引擎里**只有 `await waitUserAnswer` 会挂起**。这带来两个好处：
- 状态一致性简单（不会出现"两个 pendingAsk"）
- 可测（不需要拉起整个 Agent）

#### 三条不变量

1. 同一时刻**只能有一个** `pendingAsk`
2. `pendingAsk` 必须**同步**设置在 await 之前（否则抢跑 409）
3. 等待必须有**超时 + 断开取消**（否则用户不答 = 永久内存泄漏）

#### 分级提醒（P1-⑧）

```
30s  → 温和提醒（"占卜师还在等你"）
2min → 明确提醒
5min → 兜底收束
```

**关键：提醒不结束等待**，只是往流里推一个 `nudge` 事件。
用户看到提示，回来还能接着答 —— 如果提醒即结束，那和直接超时没区别。

**技术难点**：提醒触发在 `setTimeout` 回调里，而生成器正卡在 await 上，
**无法从回调里 yield 事件**。解法：回调只往队列塞，
等等待结束、生成器恢复控制权后，在下一轮循环顶部 flush。

代价：提醒会延后到"用户应答之后"发出（仍告诉前端"用户走神了多久"）。

#### 为什么有 5 分钟超时

用户走开 6 分钟回来，会话已死（"占卜师暂时失联"）。
分级提醒 + 兜底收束让慢用户能接着走。

### 4.4 三子 Agent 管线（Reflexion）

**文件**：`src/lib/agent/subagents.ts`

```
analyst  → 牌意分析（≤250 字，结构化笔记，不面向用户）
   ↓
writer   → 基于笔记流式撰写（逐字推送给用户）
   ↓
reviewer → 三维度打分（grounding/empathy/tone）
   ↓ 不过 → revision（修改指令）
   ↓
writer 重写 → reviewer 复检（判断新版，不是沿用旧结论）
```

#### 为什么拆三个 Agent

| Agent | 职责 | 关键参数 |
|---|---|---|
| analyst | 只读牌面 + 检索结果，产出**结论**（不写推导过程） | `thinking: disabled`（提速）、max_tokens 3000 |
| writer | 把笔记写成有温度的解读 | 流式、max_tokens 6000 |
| reviewer | 找问题并给**可执行的修改指令** | 鲁棒 JSON 解析、max_tokens 2000 |

**为什么 analyst 要关思维链？**
它是结构化任务（读牌面 → 出笔记），不需要推理链。
关掉后更快、更省 token。

**为什么 writer 反而要保留思维链？**
实测教训：无思维链时模型会跳过工具直接文本回答
（`money` 用例从 10 个 tool 调用掉到 0 个）—— 退化成聊天机器人。

#### Reflexion 的细节

**复检必须重新判定新版**，不能沿用旧结论：

```ts
let reReview: ReviewResult | null = null;
for await (const evt of runReviewer(config, session, reading)) {  // ← 传新正文
  if (evt.type === "review") reReview = evt.review ?? null;
}
```

#### 鲁棒 JSON 解析（三层兜底）

`src/lib/robust-json.ts`：
1. `JSON.parse`
2. 括号配平提取（含归一化：去掉 markdown 围栏、前后废话）
3. 字段级正则（`"grounding":\s*(\d+)`）

**为什么不能静默"默认通过"？**
审校解析失败若当成通过，等于**没有审校**却显示"审校通过"——
用户与后续流程都被误导。现在明确产出 `pass: true` 但 `comment` 标注"审校未完成"。

### 4.5 混合 RAG 检索

**文件**：`src/lib/rag-engine.ts` + `vector-engine.ts`

#### 三路召回 + RRF 融合

```
查询
 ├─ 精确通道：牌名精确匹配（用户点了「宝剑十」就必进 top-k 且置顶）
 ├─ BM25 通道：Okapi BM25，k1=1.5 b=0.75，中文 2-gram
 └─ 向量通道：ONNX 真实 embedding（384 维，量化 22MB，离线）
       ↓
   RRF 融合：score = Σ 1/(k + rank)，k=20
       ↓
   每牌去重 → top-k
```

#### 为什么精确通道要加权（EXACT_BOOST = 3）

纯 rank 叠加下（k=60，候选 10 个）rank 分差仅约 15%，
双通道命中的无关牌**可以反超** exact-only ——
"必进 top-k 且置顶"在数学上不成立。乘 3 倍才真正置顶。

#### 查询改写（关键优化）

口语查询（"复合 前任"）不含牌名，BM25 字面匹配**近零召回**
（golden set 实测 Recall@5 仅 **44.6%**）。

主题词典（`TOPIC_CARD_MAP`）补牌名候选 → **82.2%**。

```
裸检索      Recall@5 44.6%  MRR 0.556  NDCG 0.433  零命中 14
含改写      Recall@5 82.2%  MRR 0.917  NDCG 0.815  零命中 0
```

**这个 37.6 个点的差值说明**：检索层本身偏弱，是改写层在救。
这正是 P4-⑪ 想加强的方向（结论见第六节）。

#### 降级链

```
ONNX embedding → 特征哈希向量（256 维 FNV-1a）→ 纯 BM25
```

### 4.6 LLM 调用层

**文件**：`src/lib/agent/llm.ts` + `src/lib/llm-providers.ts`

这一层承担了四件事，每件都对应一类真实故障：

#### ① Failover（串行切换）

```
主用失败（网络/超时/5xx/429/401/402/403）→ 切备用
```

**为什么 401/402/403 也要切？**
这类错误**短期内不会自愈**（key 无效/余额耗尽）。死守只会让用户看到"占卜师暂时失联"。

**粘性记忆**：切换后 10 分钟内直接用备用，不再每次先吃主模型超时。

**流式安全**：仅在**首 token 前**失败才切换（已开始输出不切，避免重复推送）。

#### ② 熔断器（三态）

```
closed（正常）→ 失败 3 次 → open（跳过 60 秒）→ half-open（试探）
```

熔断与 failover 的区别：failover 是"这次换一家"，熔断是"这家最近不行，别碰它"。

#### ③ 滑动窗口限速（P1-⑦ → 2026-11 重构）

**问题**：上游网关实测配额是 **滚动 ~60 秒窗口，窗口内 4~6 次**：

```
间隔  3 秒 × 4 次 → 预热后 50 秒才放行 → 窗口 ≈ 60 秒
间隔 10 秒 × 6 次 → 第 5 次 429
间隔 15 秒 × 6 次 → 全部通过（60 秒内 4 次，安全）
```

一场占卜要打 ~14 次 LLM 往返 → **必然打满窗口** → 429 → 降级 → 质量指标失真。

**为什么第一版用令牌桶是错的？**

这是本次最有价值的教训 —— **限流器的语义必须与上游逐字一致**：

| | 上游配额语义 | 令牌桶语义 |
|---|---|---|
| 判据 | 「**最近 60 秒内**最多 4 次」 | 「空闲能攒额度」 |
| 空闲 30 秒后 | 窗口里可能还有记录占位 | 攒满 burst 个令牌 |
| 后果 | — | **攒额度 → 连发 → 同一窗口 → 429** |

实测：burst=2 的纯令牌桶，30 秒内发了 8 次，第 9 次 429。

**修复：滑动窗口成为唯一限流器**

```ts
// Bucket 增加 stamps（窗口内的请求时间戳）
const windowStart = now - RATE_WINDOW_MS;
bucket.stamps = bucket.stamps.filter((t) => t > windowStart);   // 剔除过期 = 滚动
const waitMs = bucket.stamps.length >= burst
  ? bucket.stamps[0] + RATE_WINDOW_MS - now + 50                // 等最老那条过期
  : 0;
```

语义与上游**逐字一致**：不多限，也不错放。

**为什么不叠加"最小间隔"？**
滑动窗口本身已含均摊语义（60 秒 4 次 = 每 15 秒 1 次）。
之前额外加"距上次放行 ≥ 10 秒"，结果把**合法的突发也挡了** ——
上游允许 60 秒内连发 4 次，我们只放 1 次，反而更慢且没有额外保护。

**429 自适应收紧（AIMD 乘性减）**

```
收到 429 → 容量 ×0.5（下限 0.25×，至少 1 次/窗口）→ 随时间缓慢回升（每秒 +1%）
```

⚠️ 关键：**不清空 stamps**。清空 = 窗口腾空 = 立刻再发 = 刚撞 429 就再撞。
正确做法是把窗口**填满到当前容量** → 至少等一个窗口过期再试（标准退避）。

**为什么熔断器不够？**
熔断是**事后**的（provider 已经失败才跳过），限流是**事前**的（节奏问题）。
熔断器只解决"provider 坏了"，不解决"请求太密"。

**探针脚本留档**：`scripts/probe-gateway-quota.mjs`
（配额是**环境相关**的，换网关/换 key/换时间都可能不同，必须能随时实测，
而不是靠记忆猜一个数。）


#### ④ 并行择优（Hedged Request，P1-⑥）

```
主用近期失败过 + 开关打开 → 双路同时发请求，谁先回用谁
```

**收益**：主用挂掉时，用户的第一个 token 从等 45~80 秒降到等最快那路。

**为什么默认关闭？**
并行 = 消耗**双倍配额**（输的那次请求也算数）。
只在"主用已知可能有问题"时才多花这份配额。

**落败方要主动 abort** —— 否则它会跑完（继续烧 token + 占节流槽位）。
为此 `rawCall` 增加 `externalSignal` 参数，与 `AbortSignal.timeout` 用
`AbortSignal.any` 合流。

#### 降级引擎也走完整仪式（P1-⑧ 之后）

→ rag_search → 每张：ask_user(flip) → card_reveal → delta → card_reading
→ review → ask_user(closing) → done

**为什么降级也要这么认真？**
用户看不到模型时，仪式感仍在 —— 这是"降级不删"的真正含义。
不只是"能跑"，还得"跑得像样"。

### 4.8 SSE 协议与断点续传

**文件**：`src/app/api/interpret/route.ts` + `src/lib/agent/event-log.ts`

#### 事件序号

每个事件带 SSE 标准的 `id: <seq>`（单调递增），存内存 ring buffer
（每会话 500 条 / TTL 30 分钟）。

```
id: 5
data: {"type":"tool","tool":{...}}
```

#### 断点续传

```
客户端断线 → 记录 lastSeqRef
重连 → POST /api/interpret { sessionId, resume: true }
     + Header: Last-Event-ID: <seq>
后端 → 从 ring buffer 补发 seq > lastSeq 的事件
```

**resume 请求不推进流程**（跳过 busy 互斥检查 —— 会话在跑是正常的）。

实测：seq=16 断开 → 补发 seq=17，无缝衔接 / 无缺口 / 无重复 ✅

#### ⚠️ 副作用：多行帧解析（踩过坑）

加 `id:` 字段后，后端发的是**多行帧**。
而 11 个验证脚本用单行解析（`p.trim().startsWith("data:")`）→ **整帧跳过**。

**症状极具迷惑性**："加了断点续传后所有验证脚本突然全红"——
看起来像功能崩了，实际是客户端解析器没跟上。

修法：按行拆帧找 `data:` 行（与前端 `page.tsx` 一致）。

## 五、一次真实的排查过程（比架构更能说明工程能力）

> 2026-11-02 晚：34 条评估用例全军覆没，总体通过率 2%。
> 这一节记录完整的排查链条 —— 它比任何架构图都更能说明问题。

### 5.1 第一层：看起来像"环境问题"

```
33/34 失败 · 失败类型：timeout 21 · disconnected 6 · assertion 32
```
第一反应：LLM 挂了？key 过期？网络问题？

**排查**：`.env.local` 里 `DEEPSEEK_API_KEY` 与 `FALLBACK_API_KEY` **都是空的**。
→ 恢复 key → 仍然全挂。

### 5.2 第二层：网关限流（真实原因之一）

```
429 Rate limit exceeded · Current limit: 4 · Remaining: 0
```
实测限流语义：
```
间隔 20s 连发 5 次 → 全过
间隔 12s 连发 6 次 → 全过
间隔  8s 第 5 次    → 被限流
间隔  3s 每次      → 被限流
```
→ 约 **4 次 / 30~40 秒窗口**。一场占卜 14 次调用 → 必然打满。

**但这只是表象**：为什么"重启也治不好"？

### 5.3 第三层：僵尸会话占着资源（真凶）

查数据库发现 **7 条 running 会话**，最老的 **3 天前**（5206 分钟）。

三处缺陷叠加：
1. `reconcileOnBoot()` **从未被调用**（函数存在，但 instrumentation 里只有向量预热）
2. `restoreSession` 把 `lastActive` 填成 `Date.now()` → 恢复 3 天前的会话时它"看起来刚刚活跃" → persist 又把这个假心跳写回快照 → **永久保鲜**
3. 对账判据用 `created_at`（创建时间）而非快照里的 `lastActive`（真实活跃时间）

**修复后**：running 会话 7 → 0，网关配额**立即恢复**（连续 3 次调用全过）。

> **面试讲点**：限流治不好的时候，先查**谁在占着资源**，再看**请求的节奏**。
> 熔断器只能事后跳过坏 provider，限流是事前的问题 —— 得在发请求前排队。

### 5.4 第四层：HITL 闸门抢跑（独立的第二个 bug）

现象：每场占卜都撞满 8 分钟超时。

**根因**：`yield ask_user` 在 `await waitUserAnswer` 之前 →
客户端应答时 `pendingAsk` 还没设置 → 409 → 应答被丢弃 → 等满 5 分钟 HITL 超时。

**波及范围**：5 处 HITL（承约/呼召/选牌/确认/收束/翻牌）。
之前只给翻牌闸门修过 `card_flip_ready` 的顺序，漏了其余。

### 5.5 第五层：验证脚本自身失效（最隐蔽）

加了 SSE `id:` 字段后，**11 个验证脚本收不到任何事件**——
单行解析整帧跳过。

### 5.6 第六层：指标分类失真（让排查变困难）

429 与"走本地降级"都被算成 assert 失败 → 总体通过率 2%，全是误报。

修正分类后，才暴露出真正的问题（review 维度 33%）——
**指标不可信时，数字再好看也没意义**。

### 5.7 最终结果

```
10 条真实 LLM 用例：
  总体通过率 99% · 单例均值 98.6%（标准差 2.4%）
  承约/呼召/逐张解读/收束 100%
  rag/cite/complete/review 100% · clarify 88%
```

## 六、被实测否决的三个"优化"

> 这一节是本项目最有价值的部分之一。
> **"我做了什么"人人会说，"我否决了什么、为什么"才是工程能力的证据。**

### 6.1 ❌ RAG 检索并发（Promise.all）

**原假设**：3 张牌的检索并发执行能省 24 秒。

**实测**：
```
单次 hybridSearch: 3.3 ~ 4.5ms
串行 3 次: 12.0ms   并发 3 次: 8.7ms   净节省 3.3ms
```

**根因**：`hybridSearch` 是**同步 CPU 计算**，Node 单线程里
`Promise.all` 只能并发等待、不能并行计算。

**结论**：收益 3ms，远小于 worker_threads 的复杂度。**不做**。

> 我原方案里写的"省 2~4s / 省 24s"两个数字都是错的
> （24s 来自误读时间线里的 LLM 往返时间）。**数据推翻了直觉。**

### 6.2 ❌ 字段权重进 RRF 融合

**原假设**：字段权重（keywords 1.4 > 牌意 1.2 > 叙事 1.0）
只在 BM25 内部生效，让它进入融合排序，检索会更准。

**实测**（golden set 51 条，双口径）：
```
                    不进融合（基线）    进融合（尝试）
  裸检索 Recall@5        44.6%           44.9%  (+0.3)
  裸检索 MRR             0.556           0.549  (-0.007)
  裸检索 零命中          14              15
  改写 Recall@5          82.2%           81.5%  (-0.7)
  改写 MRR              0.917           0.897
```

**根因**：`FIELD_WEIGHT` **已在 BM25 打分内部生效**
（`ragSearch` 内 `score *= FIELD_WEIGHT`），
融合层再加一遍是**重复计数**。

**结论**：无净收益，**回退**。结论写进 `fuseAndDedup` 的注释，
防止后人重复踩坑。

**检索层下一步的正确方向**是 cross-encoder rerank（对 top-20 重排），
但那需要引入新模型，超出当前性价比。

### 6.3 ❌ Supervisor 流式化

**原假设**：把决策也改成流式，首 token 提前 → 用户更快看到反应。

**实测**（glm-5.3）：
```
                  非流式            流式
  总耗时           5370ms           3925ms
  reasoning        2787 字 ✅        0 字 ❌（网关不下发）
  tool_calls       完整返回         分片到达
```

**决定性发现**：**glm 网关在流式下完全不下发 `reasoning_content`**
（也试过 `thinking:{type:"enabled"}`，同样没有）。

而流式唯一的"提前量"是 `tool_calls` 的 arguments 分片 ——
但 arguments 是 JSON，**必须拼完才能解析**，
所以用户在流式下依然看不到任何决策过程。

**结论**：**实际收益 ≈ 0**，代价是"流式 tool_calls 分片拼装"的复杂度与协议风险。
**不做**。思考链已通过非流式 `reasoning_content` 一次性获取并立即推给前端
（`if (decision.reasoning) yield { type: "reasoning" }`），这部分价值已经拿到了。

> 两个探测脚本保留在仓库里，防止后人重复评估这件事。

### 6.4 ❌ 用令牌桶限流（第一版实现，语义与上游不匹配）

**原假设**：令牌桶能表达「窗口内 N 次」的配额语义（capacity=突发次数，refillRate=补充速率）。

**实测打脸**：
```
burst=2 的纯令牌桶 → 30 秒内发了 8 次 → 第 9 次 429
```

**根因（这是最有价值的一条）**：两种限流语义**不对等**。

| | 上游配额 | 令牌桶 |
|---|---|---|
| 判据 | 「最近 60 秒内最多 4 次」 | 「空闲能攒额度」 |
| 空闲 30 秒 | 窗口里可能还有记录占位 | 攒满 burst 个令牌 → **能连发** |
| 结果 | — | 攒额度后连发 → 同一窗口 → 429 |

**结论**：**限流器的语义必须与上游逐字一致**，不能"差不多"。
纯令牌桶的"攒额度"特性在这里恰恰是**有害的**。

**修复**：改成滑动窗口（记录窗口内的请求时间戳，滚动剔除过期），
语义与上游完全一致 → 实测全程零 429。

**延伸教训**：这个 bug 还暴露了**测试钩子漂移**的问题 ——
`acquireSlotForTest` 只返回"被拦"而不预登记放行时刻，
导致窗口计数与真实行为脱节，**断言测的是另一个东西**。
测试钩子必须完整模拟真实流程（预定放行时刻 + 占窗口位置）。

> 配额探针脚本 `scripts/probe-gateway-quota.mjs` 留档 ——
> 配额是**环境相关**的，必须能随时实测，而不是靠记忆猜一个数。

## 九、公网化改造（2026-11）

> 这一章记录的是**第二轮**优化：从"功能完备"转向"能安全地放到公网上"。
> 与前面八章的区别：前面的判据是"体验好不好、指标准不准"，
> 这一轮的判据是**"放到公网上会不会出事"**。

### 9.1 为什么这轮改造的判据是"公网"

第一轮做完的时候，项目已经能跑完整仪式、指标也准了。
但把它放到公网上，会出现**第一轮的所有验证都发现不了**的问题：

| 问题 | 为什么第一轮没发现 |
|---|---|
| `/api/dashboard` 完全公开 | 本地看是"方便的运维入口"，公网看是"泄露全站用户心理内容" |
| sessionId 含时间戳可枚举 | 本地测不出"能不能被遍历" —— 需要攻击者视角 |
| 客户端可指定任意 userKey | 本地只有一个用户，写谁都行 |
| 输入无长度上限 | 本地手打 20 字，看不出 10MB 的杀伤力 |
| `/api/health` 返回绝对路径 | 本地无所谓，公网等于公布文件系统布局 |

**教训**：功能测试和攻击面测试是**两套完全不同的用例**。
前者验证"该做的做了"，后者验证"不该做的没做"。
后者只能靠**换视角**（假设你是攻击者）才能想到。

### 9.2 鉴权：能力凭证而非用户体系

**决策点**：占卜产品要不要做用户登录？

**不做的理由**：占卜是"打开网页就能用"的产品。强制登录会把
"打开 → 默念 → 占卜"这个零摩擦体验变成"打开 → 注册 → 登录 → 占卜"，
转化率会掉一个量级。而占卜结果**不需要**跨设备同步（用户不会为了看昨天的解读专门注册）。

**替代方案：能力凭证**（Capability Credentials）——
不证明"你是谁"，只证明"你有这个能力"。

| 凭证 | 授予的能力 | 强度 | 为什么这样设计 |
|---|---|---|---|
| `sessionId` | 控制会话（answer / interject） | 192bit 全随机 | 本身就是凭证，不需要额外的密码 |
| `shareToken` | 只读分享页 | 128bit，独立 | 分享出去的是**读权限**，不是**控制权** |
| `DASHBOARD_TOKEN` | 观测面板 | 环境变量 | 内部工具，不需要完整用户体系 |
| `userKey` | 跨会话画像 | IP+UA+盐 的哈希 | 服务端派生，客户端不可伪造 |

**两个关键设计细节**：

**① sessionId 从"可枚举"改成"不可枚举"**

```
旧：sess_${Date.now().toString(36)}_${random6(36)}    ← 时间戳部分可遍历
新：sess_${randomBytes(24).base64url}                   ← 192bit，2^192 空间
```

时间戳前缀让攻击者能遍历"最近一小时内创建的会话"，
而 sessionId 是**控制凭证**（能替用户回答占卜师）。

**② 分享令牌与会话凭证分离**

这是最容易漏的一条。直觉做法是"分享链接 = 把 sessionId 放进 URL"。
但 sessionId 是**控制凭证** —— 拿到它的人能：
- 替用户回答占卜师的问题（篡改解读方向）
- 插话（注入内容）
- 甚至中断会话

分享一张解读卡片，等于把控制权也给出去了。
所以引入独立的 `shareToken`：**只能读，不能控**。

### 9.3 六处泄露面与它们的修法

审计实测出的六处，逐个修：

| # | 泄露面 | 原状 | 修法 |
|---|---|---|---|
| ① | `/api/dashboard` + `/events` | 完全公开，返回全站用户问题原文与解读 | `DASHBOARD_TOKEN` 鉴权，**未配置时 fail closed** |
| ② | `/api/share?id=<sessionId>` | 可枚举的 id 直接返回私密全文 | 独立 `shareToken`（128bit）；老链接签发新令牌并提示换用 |
| ③ | `/api/interpret` 的 userKey | 客户端可指定任意值 → 读写他人画像 | **服务端派生**（IP+UA+盐 的 SHA-256） |
| ④ | 输入无长度上限 | 单请求可放大 token 成本（每轮 prompt 都重发） | question/followup/answer/body 全部设上限 |
| ⑤ | `/api/health` | `vectorStatus()` 含服务器绝对路径 | 只保留 basename |
| ⑥ | 安全响应头 | 只有 `/api/share` 有，其余全裸 | `next.config.ts` 的 `headers()` **框架级**统一配置 |

**为什么安全头放在 `next.config.ts` 而不是每个路由手写**：
逐路由手写的问题是"新增路由必然漏"—— 这正是 bug 的成因本身。
框架级声明一次，全站生效（**包括 HTML 页面**，那是路由级做不到的）。

**关于 CORS 的诚实说明**：
审计说"没有 CORS 配置"是个问题。**其实不是** ——
浏览器默认禁止跨域请求，没有 CORS 头就是"最严格的白名单（空）"。
真正需要 CORS 的场景是**前后端不同域**。所以做法是：
`CORS_ORIGINS` 环境变量为空时**不发** CORS 头（浏览器默认最严），
配置了才发，且**绝不允许 `*`**（本项目返回的是私密内容）。

### 9.4 状态收敛：globalThis 解决什么、不解决什么

审计发现项目里的跨请求状态**声明方式不一致**：
有的挂 `globalThis`（会话表、熔断器、DB 连接），
有的是模块级变量（事件缓冲、限流桶、provider 健康度、RAG 缓存、dirty 集合）。

**为什么这是功能问题而非风格问题**：
Next dev 的 HMR 会重新求值模块 → 模块级变量被重置：

| 状态 | HMR 重置的后果 |
|---|---|
| 限流窗口 | 清空 → 立刻连发一批 → 429 |
| 熔断状态 | 丢失 → 已知坏掉的 provider 又被调用 |
| SSE seq 序号 | 从头开始 → 断点续传的 `Last-Event-ID` 语义失效 |
| dirty 集合 | 清空 → 落在重载后的会话**永远不会被落快照** |

修法：新增 `src/lib/runtime.ts`，提供 `runtimeState(key, factory)` 单一入口。
**用工厂函数而不是直接赋值** —— 直接赋值在模块重复求值时会**覆盖**已有状态，
恰好是要避免的问题。

**最终收敛了 13 处状态**（`scripts/verify-runtime-state.mjs` 静态扫描保证不会有漏网的）：

| 命名空间 | 状态 | HMR 重置的后果 |
|---|---|---|
| `llm.buckets` | 限流窗口 | 清空 → 立刻连发 → 429 |
| `llm.rateStates` | 429 收紧系数 | 丢失 → 收紧失效 |
| `llm.breaker` | 熔断器 | 丢失 → 已知坏 provider 又被调用 |
| `llm.truncatedSessions` | 截断标记 | 丢失 → 截断场次被算作"通过" |
| `providers.health` | provider 健康记忆 | 丢失 → 每次重载重吃超时 |
| `session.sessions` | 会话表 | 丢失 → 用户会话凭空消失 |
| `session.dirty` | 快照脏标记 | 丢失 → 会话永远不被落快照 |
| `eventLog.buffers` | SSE 事件缓冲 | 丢失 → seq 归零 → 断点续传语义失效 |
| `rag.cache` / `rag.cacheCounters` | 检索缓存与计数 | 丢失 → 命中率统计归零 |
| `rag.df` | BM25 文档频率表 | 丢失 → 每次重载重算全表 |
| `vector.state` | 向量索引 + **并发构建防护** | 丢失 → **重复跑全量 ONNX 推理** |
| `db.dashboardCache` | 面板统计缓存 | 丢失 → 重载后第一个请求又跑全表聚合 |

**判据：模块重算后行为是否改变** —— 不改变的是**常量**（如 `PERSIST_TYPES`、
`NOISY_TYPES`、初始化用的临时 `seen`），不需要收敛；改变的是**状态**，必须收敛。

**必须诚实说明的边界**：

> `globalThis` **只能解决 HMR 热重载**，**解决不了多进程**。
> `next start` 多 worker 时每个 worker 有独立的 JS realm，
> 各自的 `globalThis` 也独立 → 状态仍然分裂。
>
> 跨 worker 要真正解决，必须把热状态外置（Redis / DB）
> 或**强制单 worker 部署**（本项目选了后者，并写进部署文档）。

把这个限制**写进代码注释和部署文档**，比含糊地说"我们用了 globalThus 所以线程安全"要诚实得多。

### 9.5 并发：TOCTOU 竞态与原子占用

**症状**：用户连点两次"追问" → 第二个请求报
`400 tool call result does not follow tool call` → **该会话之后所有追问都失败**。

**根因（TOCTOU）**：原来是**分开**的两步：

```ts
// ① 路由层：检查
if (session.busy) return 409;
// ② supervisor：设置（在生成器首次 next() 时）
session.busy = true;
```

两步之间有一个 `await` 间隙（生成器启动是异步的）→
两个并发请求**都通过检查** → 都进入 `runAgent` →
各自往 `session.messages` push 消息 → **assistant→tool 配对错位**。

**修法**：`tryAcquireSession()` 把"检查 + 占用"放在**同一个同步段**里。
Node 是单线程 —— 同步段内不可能有另一个请求插进来，所以天然原子。

> **这类 bug 的通用教训**：
> 「检查」和「设置」之间只要有 await，就是竞态。
> 修法不是"加锁"（Node 没有），而是**把两件事放进同一个同步段**。

### 9.6 仪式守卫：从 2 个工具到 8 个

**审计实测**：守卫只覆盖了 `offer_card_selection` 和 `draw_cards` 两个工具，
其余 6 个仪式工具**完全没有前置检查**。模型可以：
- 不承约直接 `reveal_card`（跳步）
- 不抽牌直接 `interpret_card`（解读不存在的牌）
- 不逐张讲完直接 `write_reading`（综合没依据）

**证据**：32/34 条 eval 用例的 contract/invocation/percard/closing 全缺。

**修法**：新增 `TOOL_PHASE_REQUIREMENT` 表（工具 → 必需阶段），
在 supervisor 的**工具分发前**统一查表判定。
单一事实源 → 加新工具时不会漏防（原实现每个分支各抄一份，必然漏）。

**加守卫时踩到的真坑**（值得单独讲）：

`completedPhases` 原本把 `synthesis` 挂在 `finished`（会话**结束**）上。
但 `close_reading` 的守卫要求 "synthesis 已完成" ——
而 synthesis 完成于 `write_reading` 结束，**早于**会话结束。

> → **守卫会永远拦截 `close_reading`** → 收束语永远不生成。
> → 而且**端到端测试才会发现**（单元测试测的是判据函数本身）。

修复：加独立的 `synthesisDone` 标记，时序正确。

> **教训**：**判据的时序必须与守卫的时机匹配**。
> "完成"这个词在不同时间点有不同的含义 ——
> `finished`（会话结束）和 `synthesisDone`（正文产出）是两个时刻。

### 9.7 假绿灯：指标本身要被验证

这一轮修的四个问题，本质上都是同一类：**指标看起来正常，实际是假的**。

| 假绿灯 | 表现 | 根因 | 修法 |
|---|---|---|---|
| 截断当成功 | `return "truncated" as "ok"` | **类型断言**骗过了编译器，调用方收到 "ok" | 把 "truncated" 纳入返回类型 + 标记表 + 移出通过率分母 |
| 审校降级当通过 | 审校失败时 `pass: true` + `scores: 0` | 根本没审校，却算作"通过" | 同样打标记，移出分母 |
| 缓存命中恒 0 | `ragCacheStats()` 返回 `{hits: 0, misses: 0}` | 计数器没实现 | 真实计数 + 命中率 |
| 假僵尸会话 | `listStaleSessions` 用 `created_at` | 与 `reconcileStaleSessions` 的判据不一致 | 两条 SQL **共用一个判据常量** |

**第一个尤其值得讲**，因为它是**我自己上一轮引入的**：

```ts
// ❌ 修复前：想修"截断被静默当成功"的问题
return "truncated" as "ok";
```

这个 `as "ok"` 让 TypeScript 编译通过、**测试全绿**，
但运行时行为完全没变 —— 调用方拿到的还是 "ok"。
**注释里写着"现在显式返回截断标记，调用方可见"，而实际上调用方看不见。**

> **教训（和上一轮限流器那个 bug 是同一类）**：
> **注释不是证据，代码才是。**
> 上一轮是"测试钩子用了正确写法、生产实现没有"，
> 这一轮是"类型断言骗过了编译器"。
> 两次的共同点：**绿色的测试和注释都不等于行为正确**。

**为什么截断/降级要移出通过率分母，而不是改成 `pass: false`**：
改成 false 会触发 Reflexion 重写 —— 但重写一份**已经截断**的正文没有意义
（模型拿到的还是残缺上下文），还会白白多烧一轮 LLM 调用。
所以保持 `pass` 不变（不阻断流程），改的是**指标口径**。

### 9.8 这轮改造的验证方式

| 脚本 | 断言数 | 验证内容 |
|---|---|---|
| `verify-api-auth.mjs` | 19 | 真实 HTTP：401/200、安全头、截断生效、sessionId 不可枚举 |
| `verify-sse-cancel.mjs` | 4 | abort 通道完整 + restart 会中断旧流 |
| `verify-resume-trigger.mjs` | 6 | 断点续传的 ref 修复（含最小复现） |
| `verify-phase-guard.mjs` | 10 | 守卫表覆盖 8 工具 + `.ok` 不被丢弃 |
| `verify-e2e-ritual.mjs` | 6 | **真实跑完一场占卜**（自动回答 HITL），零误拦 |
| `verify-rate-concurrency.mjs` | 5 | 限流器并发占位顺序 |
| `verify-fallback-parity.mjs` | 19 | 降级路径与主路径同构 |

**`verify-e2e-ritual.mjs` 是最有价值的一个** ——
它实际跑完整流程（承约→呼召→选牌→抽牌→逐张×3→综合→收束），
并**自动扮演用户回答 10 次 HITL 提问**。

它在开发中抓到了两个静态检查抓不到的真 bug：
1. `session.reading` 从未被赋值 → 前端刷新后正文变空
2. 快照缺 `reading` / `synthesisDone` → 重启后正文丢失 + 收束被拦

> **为什么必须有端到端测试**：
> "承约 → 呼召 → 选牌 → 逐张 → 综合 → 收束"是**七步有序依赖**。
> 任何一步的前置判据写错，都只有**跑完整流程**才能暴露。
> 单元测试测的是"判据函数对不对"，而 bug 在"判据用在哪、什么时候用"。

### 9.9 遗留的架构限制

| 限制 | 影响 | 缓解 |
|---|---|---|
| 单 worker | 吞吐上限 1 进程 | 热状态外置到 Redis 后可横向扩展 |
| SQLite 同步写 | 写入时阻塞事件循环 | 量大后换 PostgreSQL |
| 会话在内存 | 重启丢失活跃会话 | 快照已落 DB，重启后可恢复大部分 |
| 分享链接永久有效 | 拿到链接的人一直能看 | 可加有效期（尚未实现） |
| 无用户体系 | 无法"找回我的历史" | 画像按 IP+UA 派生（换设备即新画像） |

**这张表比"功能列表"更重要** —— 面试时能讲清楚边界在哪里，
比声称"什么都能做"可信得多。

## 附：核心设计原则速查

| 原则 | 具体体现 |
|---|---|
| 核心不变量必须后端强制 | 仪式状态机（**8 工具全覆盖**）、单工具/轮、闸门先就绪 |
| 降级不是删减 | 本地剧本引擎走完整仪式；向量→哈希→BM25；429→熔断→failover |
| 指标本身要验证 | 分类 env_error / assert；修正无效判定；**假绿灯四连修** |
| 外部语义要实测 | 配额探针 / 流式格式探针 / 思考链探针（三个脚本留档） |
| 先测再改 | 网格搜索脚本、耗时实测脚本、探测脚本 |
| 被否决的结论要留档 | 注释里写明"为什么不做"与实测数据 |
| 失败要有归属 | error_reason 分类 + 事件日志 + trace 时间轴 |
| **注释不是证据，代码才是** | 限流器钩子/实现不一致；`as "ok"` 断言骗过编译器 |
| **判据的时序要匹配守卫的时机** | `synthesisDone` ≠ `finished`（否则收束永远被拦） |
| **检查与设置之间不能有 await** | `tryAcquireSession` 原子占用 |
| **公网视角要单独测** | 功能测试与攻击面测试是两套用例 |
